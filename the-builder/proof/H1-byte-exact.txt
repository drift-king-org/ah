What happened: certutil wrote cloudflare-pid-rs/proof/M2-sha256.txt with CRLF
line endings (Windows native). Committed in fb106fd, git's global
core.autocrlf (set outside this repo, on this machine) converted it to LF
before storing the blob -- so the committed evidence was not the bytes
certutil actually produced. A Windows-side `git status`/`git checkout`
reported it as clean only because the same global setting converted it back
to CRLF on checkout, masking the mismatch. Comparing the blob itself (e.g.
from a non-Windows view) showed it changed. Proof files must never change,
including by the tool that stores them.

First fix attempted and wrong: `.gitattributes` containing `proof/** -text`.
The pattern has a slash before the `**`, which anchors it to the repo root
per gitattributes/gitignore matching rules -- it only ever matched a `proof/`
folder at the root, never `cloudflare-pid-rs/proof/` or `the-builder/proof/`.
`git ls-files --eol` showed no attribute applied to anything. Caught by
diffing the same repo from a different OS, not from more scratchpad Python.

Real fix:
  git config --local core.autocrlf false
  .gitattributes: * -text   (whole repo, not just proof/)
  git add --renormalize .

Result: only cloudflare-pid-rs/proof/M2-sha256.txt changed (i/crlf w/crlf
now, matching certutil's real output). Nothing else in the repo was ever
mis-stored -- pid1.bin, the tar, and every image were already treated as
binary; every other text file was already LF end to end.
