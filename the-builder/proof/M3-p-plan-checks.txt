M3: the plan is P-Plan (http://purl.org/net/p-plan#). Every check is two
steps, a canary-step and a real-step, chained sequentially; two command
steps (scan, extract-strings) feed the checks that read their output.
main.rs holds no SPARQL of its own: plan-steps.rq and step-precedes.rq
answer what the steps and their order are; step-input-entities.rq and
expected-outcome.rq answer what a step reads and what its outcome should
be. The one hand-written exception, as agreed, is following owl:imports
during bootstrap -- it has to run before any query can.

Real bugs found by actually running this against the model, not by
re-reading it by hand:

1. the-builder/vocab/earl.rdf declares xml:base="" at its root. oxigraph's
   RDF/XML reader takes that literally instead of resolving it against the
   parser's own base first, so every rdf:about="" or "#Fragment" in the
   file failed to parse with no base at all. Fixed in main.rs: the broken
   attribute is patched to xml:base="http://www.w3.org/ns/earl#" in the
   bytes handed to the parser only -- the vendored file on disk, and its
   sha256, are untouched.

2. p-plan:correspondsToVariable has domain p-plan:Entity (verified against
   the vendored p-plan.rdf). Every file linked to a Variable needed
   `a p-plan:Entity` asserted, the same way a step is typed both Step and
   SoftwareConfiguration -- caught by domain-retypes itself once the real
   run exercised it for the first time under M3's wiring.

3. earl:test has range earl:TestCriterion and earl:subject has range
   earl:TestSubject (verified against the vendored earl.rdf). Every check
   .rq file needed earl:TestCriterion; every canary/subject file (including
   ah.ttl itself and <not-ah/the-linter>, which needed earl:Assertor for
   earl:assertedBy) needed earl:TestSubject -- caught by range-retypes.

4. named-by-nobody.rq and code-strings-named.rq pin to ah.ttl's own
   vann:preferredNamespaceUri specifically (the M0-era multi-base
   regression fix). Reading it inside the query made a canary-step
   impossible to evaluate without loading ah.ttl alongside the canary --
   exactly what canary-isolation.rq exists to forbid. Fixed: both queries
   now take ?base as bound by the caller (substitute_variable, the same
   mechanism ?step/?plan already use), the same fix ah-workbench's own
   the-generator/queries use for their own bound variables). main.rs reads
   ?base once, from the real model, and only substitutes it into a query
   that actually projects it (checked via a light SELECT-clause text scan,
   not a SPARQL parse).

5. range-retypes.ttl (this session's own canary) was missing the
   self-contained vann:preferredNamespaceUri stand-in that domain-retypes.ttl
   already had, so it silently couldn't fire in isolation. Fixed to match.
